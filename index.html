01 write → understand → compile → ship

The compiler reads your intent.

A .vsk component is parsed, checked for semantics the target can honour, then lowered into platform code. Same source, two honest outputs.

About.vsk source 
									
									
										component About {
  <div class="max-w-3xl mx-auto px-4 py-14">
    <h1 class="text-3xl font-semibold text-ink">About Vesk</h1>
    <p class="text-muted">Some text here.</p>
  </div>
}

										<div class="max-w-3xl mx-auto px-4 py-14"><h1 class="text-3xl font-semibold text-ink">About Vesk</h1><p class="text-muted">Some text here.</p></div>

If Vesk cannot preserve the semantics of your component on a target, the build fails — it never silently ships different behaviour.

02 the philosophy

Why Vesk exists.

01

Compiler first

Guarantees move from runtime to build time. Less shipped abstraction, more known-good output.

02

One development model

A single component and styling model across targets — no per-platform rewrites of the same screen.

03

Native applications

Vesk Native compiles toward native Kotlin rather than wrapping a web app inside a WebView.

04

Developer experience

Modern tooling, fast feedback, HMR, Tailwind utilities, icons and motion primitives you already know.

05

Performance

The compiler produces optimized platform output instead of carrying a runtime abstraction along.

06

Safety

When semantics can't be preserved on a target, the compiler fails the build. Silence is the bug.
